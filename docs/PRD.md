## 1. 프로젝트 개요

단톡방 주문 대화를 붙여넣으면 갈 매장을 찾아 주문서 한 장을 만들어 준다.
주문서 한 장에는 메뉴 묶음 · 수량 · 주문한 사람 · 합계 예상 금액이 들어간다. 평가의 중심은 이 서비스를 지키는 장애 자가 복구(Auto Healing) 다.

| 구분         | 내용                                                                                                                                                                                                                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 만드는 것    | **업무 층**: LLM 에이전트 3개(Intake · Menu · Review - Menu · Review는 툴을 쓰는 에이전트)가 대화를 주문으로 바꾸고 매장 · 메뉴 · 금액은 규칙이 판정한다<br />**장애 대응 층**: LLM 없이 감지 · 진단 · 복구 · 검증을 나눠 맡는 결정적 워크플로(`healing` 서비스). 앱 복제본 장애는 게이트웨이가 먼저 정상 복제본으로 넘기고 뒤이어 자동 복구한다 |
| 쓰는 사람    | 주문 담당자(친구 · 동아리 · 가족 모임의 일반 사용자, 화면 3개) · 운영자(운영 대시보드)                                                                                                                                                                                                                                                                              |
| 주문 참여자  | 서비스에 들어오지 않는다. 단톡방에 올라온 주문서 만 본다                                                                                                                                                                                                                                                                                                               |
| 매장 기준    | 데이터 보유 브랜드 , 그 밖의 브랜드는 일반 카페로 처리                                                                                                                                                                                                                                                                                                                 |
| 입력         | 텍스트 붙여넣기 · `.txt` 파일만. 파일은 확장자가 `.txt`이고 내용이 텍스트(UTF-8 · CP949)일 때만 받는다. 이미지 · 다른 확장자(.csv · .md 등)는 받지 않고 안내 문구를 보여준다                                                                                                                                                                                   |
| 배포         | Docker Engine 1대 · compose 2개 - 공용 스택(게이트웨이 · DB · 주문 해석 서비스 · `healing`) + 같은 앱 파일로 띄운 앱 스택 A/B → 클라우드(AWS EC2 등). CI/CD가 테스트 실패 변경을 막는다                                                                                                                                                                         |
| 기간 · 인원 | 11/5 ~ 11/9 · 5명 (사전 1일 + 11/5 · 11/6 · 11/9)                                                                                                                                                                                                                                                                                                                   |

## 2. 배경과 목표

**배경**

| 누구        | 지금의 불편                                                            | 바라는 모습                                                           |
| ----------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 주문 담당자 | 약칭 · 옵션 해석, 변경 · 취소 반영, 금액 계산을 손으로 한다.         | 붙여넣기만 하면 주문서 한 장이 나온다. 바뀔 것만 반영해 공유로 끝낸다 |
| 주문 참여자 | 내 주문이 제대로 들어갔는지 알기 어렵다                                | 단톡방 카드 한 장으로 확인하고 틀리면 답장 한 줄                      |
| 운영자      | 장애를 문의가 온 뒤에야 알고 재실행 후 주문이 겹치거나 빠졌는지 모른다 | 시스템이 먼저 알아채고 고치며 정상화를 수치로 확인한다                |

**목표 6가지**

| ID  | 목표                                                                                | 수단                                                       |
| --- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| G-1 | 채팅을 넣으면 매장 기준을 자동으로 정하고 주문서까지 끊김 없이 나온다               | 매장 판별 규칙 · Intake · Menu · 규칙 검증 · 정산 계산 |
| G-2 | 정해진 장애에서 사전 허용된 조치로 자동 복구하고 MTTD · MTTR · 무인 복구율을 잰다 | Monitor · Diagnosis · Recovery Worker · Verification    |
| G-3 | 복구 전후 주문 중복 · 유실이 없고 반영한 변경과 금액이 유지된다                    | 체크포인트 재개 · 작업 ID 잠금 · 사건 lease              |
| G-4 | 고치지 못하거나 원인을 모르면 상태를 보존한 채 사람에게 넘긴다                      | 회로 차단 · 운영자 승인                                   |
| G-5 | 필수 테스트가 실패한 변경은 배포되지 않는다                                         | CI/CD 품질 게이트                                          |
| G-6 | 앱 복제본 하나가 죽어도 15초 안에 다른 복제본이 요청을 받고 세션은 DB에서 복원된다  | 게이트웨이 상태 확인 · 앱 A/B 이중화 (5.4)                |

## 3. 대상 사용자와 이용 흐름

| 사용자        | 접근 방식                                                      | 하는 일                                                        |
| ------------- | -------------------------------------------------------------- | -------------------------------------------------------------- |
| 주문 담당자   | 같은 브라우저 탭에서 쓰는 접근 토큰                            | 주문 취합 · 수정, 변경 반영, **주문서 공유 = 완료**     |
| 주문 참여자   | 접속하지 않음                                                  | 단톡방 카드에서 자기 주문 확인, 바꿀 것이 있을 때만 답장       |
| 서비스 운영자 | 담당자 화면(A · B · E) 상단 우측 [운영 대시보드] → 비밀번호 | 장애 · 복구 상태 확인, 복구 승인 · 거부, 주문 처리 기록 조회 |

- **서비스 진입 게이트(G-0)**: 어느 주소로 들어와도 처음 한 번 비밀번호를 받는다(운영 대시보드와 같은 `OPS_DASHBOARD_PASSWORD`, 비교는 서버). 통과 여부는 브라우저 세션 동안 유지되고, 운영 대시보드는 들어간 뒤에도 따로 비밀번호를 묻는다. 진입 게이트 화면에는 [운영 대시보드] 버튼이 없다. 단, 운영 대시보드 전용 주소(8502, 5.4)는 진입 게이트 없이 바로 운영 대시보드 비밀번호를 받는다(같은 값)

### 3.1 화면 구성

담당자 화면은 3개로 확인 질문 · 채팅 수정 · 변경 요청 받기는 별도 화면 없이 B와 E 안에서 처리한다.

```mermaid
flowchart LR
    A["A · 주문 시작<br/>대화 붙여넣기 · .txt"] --> B["B · 주문 정리<br/>채팅 + 주문서 패널<br/>확인 질문 · 채팅 수정"]
    B --> E["E · 주문서<br/>주문서 · 정산 통합<br/>공유 = 완료"]
    E -->|"바꿀 것이 생기면"| B
    O["O · 운영 대시보드<br/>사건 · 승인 · 지표 · 처리 기록"]
    A -.->|"상단 우측 버튼 + 비밀번호"| O
```

### 3.2 이용 흐름

```mermaid
sequenceDiagram
    autonumber
    actor 담당자
    participant 서비스
    actor 참여자 as 참여자(단톡방)

    담당자->>서비스: 대화 붙여넣기 (화면 A)
    서비스->>서비스: 매장 판별 · 이벤트 추출 · 메뉴 정규화 · 검증
    서비스-->>담당자: 확인 질문 한 번에 하나씩 (화면 B)
    담당자->>서비스: 답하기 또는 채팅으로 수정
    서비스-->>담당자: 바로 반영 + 되돌리기
    서비스-->>담당자: 주문서 한 목록 (화면 E)
    담당자->>참여자: 공유하기 = 완료 (텍스트 복사 · 이미지 저장)
    참여자-->>담당자: 바꿀 것만 답장
    담당자->>서비스: 답장 붙여넣기
    서비스-->>담당자: 분명한 변경은 바로 반영 + 되돌리기
    서비스-->>담당자: 불분명한 것은 확인 질문 (화면 B)
    담당자->>서비스: 답하기
    담당자->>참여자: 다시 공유
```

- 답장을 붙여넣으면 **분명한 변경은 바로 반영**하고 건마다 되돌리기를 남긴다. 누구의 어느 주문인지 불분명한 것은 확인 질문으로 올리고 그 항목은 확인 필요가 된다. 담당자가 제안마다 [반영] · [무시]를 누르지 않는다
- 공유 조건 3가지(서버가 공유 · 완료 처리 때 다시 확인한다):
  1. 확인 필요 항목 0건 — 모든 항목이 규칙 검증을 통과했다(= 검증 완료 · 미해결 확인 0건)
  2. 반영 여부를 정하지 않은 제안 0건
  3. 정산 정합 — 금액 미정 항목 0건이고 개인 합계 = 전체 금액
- 조건을 못 맞추면 주문서는 그대로 보이고 [공유하기]만 막히며 막힌 이유를 한 줄로 보여준다(예: "확인이 필요한 주문이 1건 있어요")
- 처음 쓰는 사람도 붙여넣기 → [정리하기] 2회(되묻기가 나오면 3회) 만에 정리를 시작한다

### 3.3 산출물

| 항목             | 내용                                                                        |
| ---------------- | --------------------------------------------------------------------------- |
| 형태             | 주문서와 정산을 한 목록으로 통합 - 같은 메뉴 · 옵션 · 기타 요청끼리 묶음  |
| 보여주는 것      | 묶음 수량 · 묶음 예상 금액 · 주문한 사람 이름 · 합계(잔 수 · 예상 금액) |
| 보여주지 않는 것 | 탭 분리 · 개인별 금액(계산과 "개인 합계 = 전체 금액" 검증은 내부에서 유지) |

| 금액 표기        | 매장 기준과 무관하게 항상 "예상" · 화면에서 가장 큰 숫자는 인원과 잔 수    |
| 처리 기록        | 변경 이력 · 복구 결과는 담당자 화면이 아니라 운영 대시보드에서 본다        |

## 4. 매장 기준 판별

화면에서 브랜드를 고르지 않는다. 대화 원문(필요하면 끝에 적는 매장 요청 한 줄, 예: "스타벅스로 갈 예정이야")에서 규칙(별칭 사전) 으로 찾는다.

```mermaid
flowchart TD
    S([대화 입력]) --> Q1{"대화 끝 매장 요청에<br/>매장 이름이 있는가"}
    Q1 -->|있다| J["요청만 보고 판정<br/>나머지 대화는 보지 않는다"]
    Q1 -->|없다| Q2{"대화 전체에<br/>매장 이름이 있는가"}
    Q2 -->|있다| J2["대화로 판정<br/>대화에서 '스타벅스'를 찾았어요"]
    Q2 -->|없다| G3["일반 카페<br/>매장 이름이 없어 일반 카페 메뉴로 정리했어요"]
    J --> R{"어떤 이름이 나왔나"}
    J2 --> R
    R -->|스타벅스만| SB["스타벅스"]
    R -->|일반 카페 표현만| GC["일반 카페"]
    R -->|미지원 브랜드만| UN["일반 카페 + 안내<br/>메가커피 메뉴는 아직 없어요"]
    R -->|"스타벅스 + 다른 매장<br/>(일반 카페 표현 포함)"| ASK["모달로 한 번 묻기<br/>스타벅스 · 일반 카페 · 기타"]
    ASK -->|"기타(직접 입력)"| GC
```

| 매장 기준                         | 별칭 사전(`backend/sql/10_seed_brand.sql`)                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 스타벅스 (`starbucks`)          | 스타벅스 · 스벅 · 스타벅스커피 · starbucks · sbux (대소문자 · 띄어쓰기 무시)                        |
| 일반 카페 (`generic`)           | 일반 카페 · 개인 카페 · 동네 카페 · 카페 ("카페 라떼"처럼 메뉴 이름 속 "카페"는 매장으로 보지 않는다) |
| 미지원 브랜드 → 일반 카페 + 안내 | 공차 · 이디야 · 메가커피 · 투썸플레이스 · 빽다방 · 컴포즈커피 · 커피빈 · 폴바셋 · 할리스 등      |

**판별 근거 문구** — 화면 B 머리에 보여준다

| 판정 경로             | 문구                                                                          |
| --------------------- | ----------------------------------------------------------------------------- |
| 매장 요청 줄에서 찾음 | '{요청 줄 원문}'에서 찾았어요                                                 |
| 대화 본문에서 찾음    | 대화에서 '{매장 이름}'를 찾았어요 (메시지 원문이 아니라 매장 이름을 보여준다) |
| 일반 카페 표현        | '일반 카페' 기준으로 정리했어요                                               |
| 미지원 브랜드         | {브랜드} 메뉴는 아직 없어 일반 카페 메뉴로 정리했어요                         |
| 매장 이름 없음        | 매장 이름이 없어 일반 카페 메뉴로 정리했어요                                  |

- **매장 요청 줄**: 대화의 마지막 줄이 `[이름] 메시지` 형식이 아니면 요청 줄로 본다
- 판별이 틀렸으면 화면 B 채팅에 "일반 카페로 해줘" · "스타벅스로 해줘" 라고 보낸다. 결과를 새로 만들므로 이때만 "새로 정리할까요?"를 한 번 묻는다
- 스타벅스는 톨 · 그란데 · 벤티, 일반 카페는 레귤러 · 라지처럼 사이즈와 옵션 가격이 다르기에 분석 전에 매장 기준을 하나로 정한다

**메뉴 매칭 결과에 따른 처리**

| 결과                                        | 처리                                                       |
| ------------------------------------------- | ---------------------------------------------------------- |
| 메뉴 데이터에 있다                          | 매칭하고 세션에 메뉴 버전을 기록                           |
| 없다(미등록 · 다른 브랜드 · 카페 외)      | 확인 필요 - 메뉴를 고르게 한다. 자동 확정 0건              |
| 후보가 여럿 · "달달한 걸로" 같은 특성 표현 | 임의로 고르지 않고 특성 태그로 후보 순서만 정리해 보여준다 |

## 5. 시스템 구성

업무 층과 장애 대응 층으로 나뉜다. 같은 장애에 항상 같은 판정이 나와야 탐지 · 복구 시간을 반복해서 잴 수 있기 때문이다.
장애 대응 층은 업무 요청 처리와 분리된 `healing` 서비스로 돌고, 업무 데이터를 직접 고치지 않으며 사전 허용된 조치만 호출한다.

```mermaid
flowchart LR
    subgraph BIZ["업무 층 · 멀티 에이전트 (보호 대상 서비스)"]
        direction LR
```

### 5.1 업무 층 멀티 에이전트

자연어 해석이 필요한 단계만 LLM 에이전트로 만든다 - Intake Agent · Menu Agent · Review Agent 3개다. 규칙으로 충분한 역할은 LLM으로 만들지 않는다.

| 에이전트     | 형태                 | 쓰는 툴                                                    | 툴 호출 상한 | 스스로 하는 판단                                                        | 하지 못하는 것                       |
| ------------ | -------------------- | ---------------------------------------------------------- | ------------ | ----------------------------------------------------------------------- | ------------------------------------ |
| Intake Agent | 구조화 출력 에이전트 | 없음 (메뉴판을 보지 않는다)                                | 0            | 메시지마다 이벤트 유형 · 연결 대상 · 원문 근거                        | 메뉴 · 가격 판정                    |
| Menu Agent   | 툴 사용 에이전트     | `search_menu` · `find_menu_by_traits` · `get_menu` | 라운드 3     | 어떤 툴로 무엇을 찾을지, 원문을 메뉴 · 요청 부분으로 나누기, 후보 정렬 | 메뉴 확정 - 확정은 규칙이 한다       |
| Review Agent | 툴 사용 에이전트     | `list_order_items` · `get_order_item` · `get_menu` | 라운드 3     | 모호한 변경 · 취소가 어느 주문을 가리키는지 의견 · 사유               | 검증 상태 변경 - 통과 · 실패는 규칙 |

- Menu · Review Agent는 판단 → 툴 호출 → 결과 확인을 최대 3라운드 되풀이한다. 다만 확정은 규칙이 한다 - 툴을 쓰는 에이전트이면서 판정은 규칙이다
- 세 에이전트 모두 세션 · 매장 같은 식별자를 인자로 받지 않는다 — 툴이 세션에서 주입받는다
- 코드 이름: Intake · Menu Agent는 `intake` · `menu`, Review Agent는 `validation`(Validation 보조 검토)이다(`llm_history.agent` 값)
- 에이전트 사이 Handoff 필드(작업 ID · 보낸 쪽 · 받는 쪽 · 시도 횟수 등)는 D-12에서 정의한다. 재시도할 때 이전 실패 원인을 넣지 않는 지금 동작(같은 입력으로 다시 생성)은 그대로 둔다

| 구성요소                    | 형태                  | 맡는 일                                                                                     | 하지 않는 일                                                                      |
| --------------------------- | --------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 매장 기준 판별              | 규칙(별칭 사전)       | 대화에서 매장 기준을 정하고 근거를 남김, 엇갈리면 모달로 한 번 묻기                         | LLM 호출, 브랜드 선택 UI                                                          |
| 업무 Orchestrator           | 상태기계              | 단계 순서 · 분기, 체크포인트 저장, 출력 형식 검사                                          | 주문 해석 · 수정, 복구 실행                                                      |
| 처리 계획 (Planner · N-02) | 규칙                  | 분석 1회의 실행 계획 작성 — 재개 여부 · 해석 서비스 · 묶음 분해 · LLM 예산 · 완료 조건 | LLM 호출, 주문 해석 · 수정                                                       |
| Intake Agent                | LLM 에이전트(툴 없음) | 메시지를 주문 이벤트로 바꾸고 앞선 주문과 연결                                              | 메뉴 · 가격 판정, 모호한 변경을 임의 확정                                        |
| Menu Agent                  | 툴 사용 LLM 에이전트  | 원문 표현을 매장 기준 메뉴 · 사양 · 옵션으로 맞춤                                         | 없는 메뉴 · 가격 만들기, 다른 브랜드 메뉴 쓰기                                   |
| Validation                  | 규칙 + Review Agent   | 누락 · 중복 · 옵션 · 수량 · 변경 관계 검사                                              | LLM 의견만으로 통과                                                               |
| Settlement                  | 계산 규칙             | 묶음별 수량 · 예상 금액 집계, 개인 합계 = 전체 금액 내부 검증                              | 합계 불일치 때 공유(완료) 허용 — 주문서는 보이되 공유가 막힌다, 개인별 금액 표시 |

### 5.2 장애 대응 층 역할 분리

한 역할이 혼자 판단 · 실행 · 종료하지 못하게 나눴다. 판단은 Diagnosis, 실행은 Recovery Worker, 종료(`recovered`)는 Verification만 한다.

| 역할                        | 하는 일                                                                                                                                                                                                   | 못 하는 일                                                      |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Gateway                     | 앱 스택 A/B 상태 확인(같은 스택 backend `/health`), 정상 스택에 요청 분산, 비정상 스택 제외 · 재등록 — Recovery보다 먼저 사용자 트래픽에서 격리                                                       | 업무 데이터 복구, 실패한 요청 재처리                            |
| Monitor                     | 유형별 메트릭(컨테이너 · 네트워크 · DB · API · LLM · 프롬프트) 관찰, 임계값 초과 시 사건 생성, 같은 대상 · 원인의 열린 사건이 있으면 증거만 추가                                                    | 설정 · 임계값 변경, 복구                                       |
| Diagnosis                   | 고정 결정표로 장애 코드 7종 중 하나로 분류(8.1), 복구 계획 작성(전략 순서 · 시도 상한 · 완료 조건), `UNKNOWN`은 승인 대기로                                                                           | 직접 복구, 복구 정책 밖 전략을 계획에 넣기, LLM으로 명령 생성   |
| Recovery Worker             | 사건 lease 획득 후 복구 계획대로 허용목록 액션만 실행(재시도 · 전환 · 재시작 · 재연결 · 재생성 · probe). 실행 순서 · 시도 횟수 · 회로 상태 · 재실행 금지 · 5분 제한 관리(종전 Orchestrator 책임) | 스스로 복구 완료 선언, 임의 셸 · Docker 명령, 업무 데이터 수정 |
| 허용목록 액션 어댑터        | 고정된 컨테이너 이름(`moa-a-backend-1` · `moa-b-backend-1` 등)에 대한 재시작 · 상태 확인만 노출. Docker 소켓은 재시작만 허용하는 프록시를 거친다                                                    | 허용목록 밖 대상 · 동작, 컨테이너 생성 · 삭제 · 이미지 변경  |
| Verification                | 조치 실행과 독립된 모듈에서 연속 정상 · 기능 샘플 · 데이터 무결성 확인 - 사건은 이 판정으로만 닫는다                                                                                                    | 복구 실행                                                       |
| Notification(운영 대시보드) | 결과 · 승인 요청 게시, 승인 · 거부 기록. 승인 API는 상태만 전환하고 액션은 Recovery Worker가 실행                                                                                                       | 정책 변경, 복구 실행                                            |

> **복구 경계** (2026-11-06 결정): 요청 안 복구(재시도 · 대체 전환 · 캐시 폴백 · 출력 재생성)는 **업무 층**이
> 요청 안에서 실행하고 회로 상태 · 사건 증거로 남긴다. Recovery Worker는 그 신호로 프로세스 수준 조치
> (허용목록 재시작 · 회로 개폐 · probe · 에스컬레이션)만 한다. 두 층이 함께 재시도하면 시도 상한(FR-016)이 깨진다.

### 5.3 Planner — 처리 계획 · 복구 계획

두 층 모두 Planner를 규칙으로 둔다. 할 일의 종류는 고정이고 계획이 달라지는 것은 입력 크기 · 서비스 상태 · 장애 코드이기 때문이다.

| 항목                | 업무 층 - 처리 계획                                                                    | 장애 대응 층 - 복구 계획                                                              |
| ------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 언제                | 분석 · 채팅 · 답장 1회마다, LLM 호출 전                                              | 사건 분류 직후, Recovery 실행 전                                                      |
| 입력                | 메시지 목록 · Intake 저장본 유무 · 회로 상태 · 설정 상한                            | 장애 코드 · 증거 · 시도 이력 · 회로 상태                                           |
| 작업 분해           | 메시지를 묶음으로 나눈다(1차 4건 · 대체 2건), 묶음마다 앞 문맥 · 같은 사람 문맥 첨부 | 복구 정책에서 그 장애의 전략을 단계로 펼친다(예: 재시도 3회 → 대체 2회 → 규칙 폴백) |
| 순서 · 건너뛰기    | Intake 저장본이 있으면 Intake 단계를 건너뛴다(재개)                                    | 냉각시간 · 회로가 열린 전략은 계획에서 뺀다                                          |
| 자원 배분           | 해석 서비스(1차 · 대체 · 규칙) 선택, LLM 호출 300회 예산 안에서 묶음별 배정          | 시도 상한 · 사건 전체 5분 · 역할별 타임아웃                                         |
| 완료 조건           | 모든 메시지에 이벤트 1개 이상 · 스키마 통과 · 체크포인트 저장                        | 그 장애의 성공 검증 기준 — 판정은 Verification                                       |
| 결과물              | `plan` — 로그와 세션 계측에 기록                                                    | `recovery_plan` — 사건 레코드에 기록, 운영 대시보드에 표시                         |
| 금지                | LLM 호출, 주문 해석 · 수정                                                            | 복구 실행, 복구 정책 밖 전략                                                          |
| 계획대로 안 됐을 때 | 계획과 실제 실행의 차이를 `degraded`로 남긴다                                        | 단계가 실패하면 계획의 다음 단계로, 소진되면 `failed` 또는 `awaiting_approval`    |

- **역할을 나눈다.** 조정 · 종료 판단(Supervisor)은 Orchestrator가(장애 대응 층은 Recovery Worker가), 분해 · 순서 · 완료 조건(Planner)은 계획이 맡는다
- **계획을 결과물로 남긴다.** `plan` · `recovery_plan`을 기록해 무엇을 하기로 했고 실제로 무엇을 했는지 대조할 수 있게 한다

### 5.4 배포 구성 — 공용 스택 + 앱 스택 A/B (Docker Engine 1대)

Docker Engine 한 대에 compose 파일 2개로 띄운다. 앱 파일 하나를 프로젝트 이름만 바꿔 두 번 띄워 앱 복제본 A · B를 만들고 공용 스택의 게이트웨이가 두 앱 스택에 요청을 나눈다. 같은 앱 파일을 덮어쓰기 파일(`docker-compose.ops.yml`)과 함께 한 번 더 띄워 운영 대시보드 전용 스택(`moa-ops`)을 둔다.

| 공용 `healing`                            |        1 | `moa_core` 전용, 외부 포트 없음                                                   | Monitor · Diagnosis · Recovery Worker · Verification 실행. 컨테이너 조회 · 재시작은 `socket-proxy`를 거친다(Docker 소켓 직접 연결 금지) |

| 앱 `frontend`                             | 스택당 1 | 자기 스택 네트워크 전용, 포트 열지 않음                                             | Streamlit 화면. 같은 스택의 `backend`만 부른다 · `unless-stopped`                                                                        |
| 앱 `backend`                              | 스택당 1 | 자기 스택 네트워크 + `moa_core`                                                   | FastAPI · 업무 층 에이전트 · `restart: "no"`(F-3 주입 대상, 재시작은 Recovery Worker의 허용목록 액션만)                                   |
| 운영 `frontend` · `backend` (`moa-ops`) |     각 1 | `moa-ops_default` + backend는 `moa_core`. frontend만 외부 `8502`(모두에게 공개)       | 운영 대시보드 전용. 게이트웨이를 거치지 않고 앱 A · B와 장애를 같이 겪지 않는다. 장애 주입 · healing 허용목록 밖 · 둘 다 `unless-stopped`  |

- **DB는 하나다.** `db` · 볼륨을 앱 파일에 두지 않는다. 앱 파일에 두면 프로젝트마다 DB가 따로 생겨 전환 뒤 세션 복원과 SC-5가 깨진다
- **스택끼리 섞이지 않게 한다.** frontend는 자기 스택 네트워크에만 붙여 같은 스택의 `backend`만 보이게 한다. 게이트웨이와 healing은 서비스 이름이 아니라 컨테이너 이름(`moa-a-frontend-1` · `moa-a-backend-1` 등)으로 대상을 지정한다
- **상태 확인과 전환.** 게이트웨이는 사용자 요청을 각 스택의 frontend로 보내고 상태 확인은 같은 스택 backend의 `/health`를 2초 간격으로 본다(frontend 연결 실패도 장애로 본다). 2회 실패하면 그 스택을 제외하고, 앱 스택 하나의 장애는 **15초 안에** 다른 스택으로 넘긴다. 복구된 스택은 2회 연속 성공한 뒤에만 재등록한다
- **운영 대시보드는 따로 산다.** A · B는 같은 이미지라 같은 원인으로 함께 죽을 수 있는데, 그때가 복구 승인이 가장 필요한 때다. 또 ops 토큰은 backend 메모리에만 있어 A → B 전환 때 다시 로그인해야 한다. 그래서 운영자는 게이트웨이 대신 `moa-ops`(8502)로 들어가 늘 같은 backend 하나에 붙는다. 배포는 A · B가 모두 UP이 된 뒤 마지막에 교체한다
- **시작 순서.** compose의 `depends_on`은 프로젝트를 넘지 못하므로 공용 스택을 먼저 띄운다. backend는 DB가 늦게 떠도 재연결하고, 게이트웨이는 앱 스택이 없어도 먼저 뜬다
- 화면 상태는 Streamlit 메모리로 복구하지 않는다. 다시 접속하면 세션 토큰으로 DB에서 주문 · 진행 상태를 다시 불러온다
- 두 앱 스택의 로컬 메뉴 캐시는 메뉴 버전으로 구분하고 캐시만으로 불확실한 메뉴를 확정하지 않는다
- 비밀값 원본은 루트 `.env` 한 곳, 서비스마다 필요한 변수만 주입한다
- 실행 호스트 · 게이트웨이 · DB 자체의 장애는 이번 범위 밖이며 앱 복제본 복구율과 분리해 기록한다

### 5.5 주문 해석 서비스 (Interpreter) - Primary · Backup

주문 해석 서비스는 단톡방 대화의 주문 문장을 LLM으로 읽어 정해진 형식의 데이터(JSON)로 바꾼다. Intake · Menu · Review Agent는 LLM을 직접 부르지 않고 이 서비스를 거친다.

| 입력 (대화 원문)                     | 해석 결과 (주문 이벤트)                                                                  |
| ------------------------------------ | ---------------------------------------------------------------------------------------- |
| 민지: "아이스 아메리카노 2잔 주세요" | `add` · 주문자 민지 · 메뉴 표현 "아메리카노" · 온도 "아이스" · 수량 2 · 원문 근거 |

| 계통             | 컨테이너                | 맡는 일                                                                           | 장애 주입         |
| ---------------- | ----------------------- | --------------------------------------------------------------------------------- | ----------------- |
| Primary (기본)   | `interpreter-primary` | 평소 해석을 모두 맡는다                                                           | F-1 · F-2 · F-5 |
| Backup (예비)    | `interpreter-backup`  | Primary 장애 때 대신 해석한다. Primary와 다른 계열 모델, 같은 입출력 형식         | 없음              |
| 규칙 해석 (폴백) | — (업무 처리 코드 안)  | Primary · Backup이 모두 실패하면 LLM 없이 규칙으로 해석해 분석을 끝까지 진행한다 | —                |

- **같은 계약.** 두 계통은 같은 입출력 형식을 쓴다. 전환은 호출 주소 교체로 끝나고, 에이전트 코드는 어느 계통이 답했는지 몰라도 된다
- **결과를 믿지 않는다.** 해석 결과는 호출하는 쪽이 정해진 형식으로 다시 검사한다. 형식이 맞지 않으면 다음 단계로 넘기지 않는다(F-5)
- **재시도는 한 곳에서.** 해석 서비스를 부르는 쪽은 재시도하지 않는다. 재시도 · 전환은 Recovery Worker가 하고(5.2), 업무 층은 회로 상태를 보고 사용할 계통만 고른다(5.3 처리 계획). 두 곳에서 세면 실제 호출 횟수를 알 수 없다
- **기록.** 어느 계통 · 모델이 답했는지 호출마다 남긴다. 대체 · 폴백 사용 비율은 운영 대시보드에 표시한다

| 장애              | 자동 복구 동작                                                                                        | 복귀 조건                       |
| ----------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------- |
| F-1 HTTP 5xx      | Primary 재시도(1 · 2 · 4초, 최대 3회) → 실패 시 Backup 전환(최대 2회) → 그래도 실패하면 규칙 해석 | Primary 상태 점검 3회 연속 정상 |
| F-2 5초 초과 지연 | 타임아웃 재시도(F-1과 같은 간격 · 횟수) → 실패 시 Backup 전환 → 그래도 실패하면 규칙 해석          | F-1과 같음                      |

정책 수치 전체는 8.1 · 8.4가 정본이다.

## 6. 업무 처리 흐름

**입력** (대화 끝 매장 요청: "스타벅스 기준으로 정리해줘")

```text
[김민수] 아이스 아메리카노 톨 2잔, 하나는 샷 추가요.
[이지연] 바닐라라떼 큰 거 얼음 적게요.
[박서연] 아아 톨 한 잔이요.
[김민수] 아까 샷 추가한 한 잔 취소할게요.
[이지연] 사이즈는 벤티로 할게요.
```

| 단계         | 하는 일                                               | 이 예시에서는                                                                                       |
| ------------ | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1 매장 판별  | 매장 요청 · 대화에서 매장을 찾는다                   | 매장 요청에 "스타벅스" 1종 → 스타벅스 기준                                                         |
| 2 처리 계획  | 재개 여부 · 해석 서비스 · 묶음 · LLM 예산을 정한다 | 저장본 없음 → 처음부터, 메시지 5개를 1차 서비스 묶음 2개로 나눔                                    |
| 3 Intake     | 메시지를 주문 이벤트로                                | 1~3줄 추가, 4줄은 1줄의 샷 추가 잔 취소, 5줄은 2줄 사이즈 변경                                      |
| 4 Menu       | 스타벅스 메뉴에 맞춘다(툴 사용)                       | "아아" → 아이스 아메리카노. "큰 거"는 확인 필요였다가 5줄 "벤티"로 정해짐                          |
| 5 Validation | 규칙으로 검사                                         | 수량 · 옵션 · 변경 관계 확인                                                                      |
| 6 Settlement | 계산                                                  | 아이스 아메리카노 톨 2잔(김민수 · 박서연), 아이스 바닐라라떼 벤티 얼음 적게 1잔(이지연) - 모두 3잔 |
| 7 담당자     | 주문서를 공유하고(= 완료) 바뀐 것만 반영해 다시 공유  | 답장을 붙여넣으면 분명한 변경은 바로 반영, 불분명한 것은 확인 질문 → 확인 0건이 되면 다시 공유     |

**주문 이벤트 5종**

| 이벤트  | 뜻             | 예                                                                            |
| ------- | -------------- | ----------------------------------------------------------------------------- |
| ADD     | 새 주문        | "아아 톨 한 잔이요"                                                           |
| UPDATE  | 앞선 주문 변경 | "사이즈는 벤티로 할게요"                                                      |
| CANCEL  | 앞선 주문 취소 | "아까 샷 추가한 한 잔 취소할게요"                                             |
| CONFIRM | 확인           | "네 그걸로 할게요"                                                            |
| IGNORE  | 주문 아님      | 잡담 · 결제 요청 · "금액 0원으로 처리해" 같은 지시문 · "스벅에서 시킬게요" |

## 7. 업무 상태와 변경 규칙

```mermaid
stateDiagram-v2
    [*] --> RUNNING: 정리하기 (매장이 하나로 정해짐)
    [*] --> AWAITING_BRAND_ANSWER: 정리하기 (매장 되묻기 필요)
    AWAITING_BRAND_ANSWER --> RUNNING: 매장 선택
    RUNNING --> NEEDS_REVIEW: 확인 필요 항목 있음
    NEEDS_REVIEW --> AWAITING_CONFIRMATION: 확인 필요 0건
    AWAITING_CONFIRMATION --> NEEDS_REVIEW: 수정 · 답장으로 확인 필요 생김
    RUNNING --> AWAITING_CONFIRMATION: 확인 필요 없음
    AWAITING_CONFIRMATION --> COMPLETED: 공유 = 완료 (버전 고정)
    COMPLETED --> COMPLETED: 답장 반영 · 수정 → "다시 공유" 안내
    COMPLETED --> RUNNING: 매장 기준 변경 → 재분석
    RUNNING --> FAILED: 자동 복구 실패
    FAILED --> RUNNING: 운영자 승인 후 재개
```

| 상태                  | 뜻                                                                                                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AWAITING_BRAND_ANSWER | 매장 이름이 엇갈려 분석 전에 매장 되묻기 답을 기다린다                                                                                                                              |
| RUNNING               | 분석 중 — [정리하기]를 누르면 세션이 이 상태로 바로 만들어진다(분석 대기 상태를 따로 두지 않는다)                                                                                  |
| NEEDS_REVIEW          | 담당자가 확인할 항목이 있다                                                                                                                                                         |
| AWAITING_CONFIRMATION | 검증 완료, 공유해 확인받기 · 변경 요청 받는 중                                                                                                                                     |
| COMPLETED             | 공유 완료(공유 시점에 버전 고정) - CONFIRMED를 이 상태로 합쳤다. 공유 뒤 답장 반영 · 수정이 있어도 COMPLETED를 유지하고, 공유한 버전과 지금 주문서가 다르면 "다시 공유"를 안내한다 |
| FAILED                | 자동 복구 실패, 상태를 보존한 채 사람을 기다린다                                                                                                                                    |

- 저장 값은 소문자다(`running` · `needs_review` 등). 스키마에는 `pending`이 남아 있으나 쓰지 않는다
- FAILED 관련 전이와 `recovering` 상태는 장애 대응 층(8.2) 구현 때 확정한다

**언제 무엇을 바꾸면 무엇을 다시 하나**

| 시점            | 매장 기준을 바꾸면 (채팅 "일반 카페로 해줘")         | 주문 항목을 고치면                                                                  |
| --------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 분석 전         | 자유롭게 변경(대화 끝 매장 요청 수정 → 판별 재실행) | -                                                                                   |
| 분석 후         | "새로 정리할까요?" 한 번 확인 후 재분석, 원문 유지   | 고친 항목만 재검증 · 바로 반영 + 되돌리기                                          |
| 공유(= 완료) 후 | 재분석(RUNNING으로) · 전체 다시 공유 안내           | 고친 항목만 재검증 · 바로 반영 + 되돌리기, 상태는 COMPLETED 유지 · 다시 공유 안내 |

## 8. 장애 시나리오와 자동 복구

목표는 사전 허용된 복구 동작을 자동으로 실행하고, 실패하거나 안전한 판단이 불가능하면 멈춰 운영자에게 넘기는 것이다. 성공 여부는 기능이 있다는 설명이 아니라 장애 시험 결과와 로그로 입증한다(9절).
메트릭 · 임계값 · 스크립트 명세 · 로그 기록은 [자동장애복구_계획서v0.md](자동장애복구_계획서v0.md) 4 ~ 6절, 제어 흐름은 [자동복구_흐름설계서v0.md](자동복구_흐름설계서v0.md) 3 ~ 7절이 정본이다.

### 8.1 대상 장애와 복구 정책

| ID  | 장애 (재현 방법)                                                      | 장애 코드                | 복구 스크립트              | 1차 복구                                                                     | 2차 복구                                           | 상한                       | 성공 판정                                          |
| --- | --------------------------------------------------------------------- | ------------------------ | -------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------- | -------------------------- | -------------------------------------------------- |
| F-1 | HTTP 5xx (모의 서비스 오류 모드)                                      | `DEP_HTTP_5XX`         | `retry_fallback.py`      | 1 · 2 · 4초 간격 재시도                                                    | 대체 서비스 전환 → 실패 시 규칙 해석 폴백         | 1차 3회 · 대체 2회        | 상태 점검 3회 연속 정상 · 검증 요청 5건 실패 없음 |
| F-2 | 5초 초과 지연 (지연 모드)                                             | `DEP_TIMEOUT`          | `retry_fallback.py`      | F-1과 같음(timeout 재시도)                                                   | 대체 서비스 전환 → 실패 시 규칙 해석 폴백         | F-1과 같음                 | 응답 시간이 기준선의 2배 이내                      |
| F-3 | 앱 프로세스 · 복제본 중단 (앱 스택 A 또는 B의 backend 컨테이너 종료) | `WORKER_DOWN`          | `restart_resume.py`      | 게이트웨이가 다른 앱 스택으로 전환 → 허용목록 대상만 재시작(준비 대기 30초) | 마지막 체크포인트부터 재개                         | 10분 안에 재시작 2회       | 중복 · 유실 없음, 반영한 변경 보존                |
| F-4 | 같은 장애 반복                                                        | `REPEATED_FAILURE`     | `circuit_probe.py`       | 3회 연속 실패 시 회로 차단                                                   | 60초 뒤 시험 요청(probe) 1회                       | probe 실패하면 운영자 승인 | 회로 상태 · 에스컬레이션 기록                     |
| F-5 | 잘못된 에이전트 출력 (필드 누락)                                      | `AGENT_OUTPUT_INVALID` | `regenerate_validate.py` | 같은 입력 · 같은 prompt version으로 재생성                                  | 확인 필요(`NEEDS_REVIEW`)로 담당자에게           | 재생성 2회                 | 재생성 출력이 형식 검사 통과                       |
| F-6 | 메뉴 저장소(DB) 조회 실패 (연결 차단)                                 | `DB_UNAVAILABLE`       | `reconnect_cache.py`     | 1 · 2 · 4초 간격 재연결 · 연결 풀 재생성                                  | 세션에 고정된 메뉴 버전 캐시로 읽기 전용 조회 계속 | 재연결 3회                 | DB 정상 · 캐시와 DB 결과 일치 · 중복 · 유실 0건 |
| -   | 모호하거나 미등록된 장애 증거                                         | `UNKNOWN`              | 자동 실행 없음             | `awaiting_approval`                                                        | 운영자 승인 · 거부                                | -                          | 승인 대기 전환 100%                                |

- F-1 · F-2 · F-3 · F-5 · F-6이 복구 가능 5종으로 무인 복구율(SC-4)의 분모다. F-4는 별도 안전성 시험으로 25회 분모에 넣지 않는다
- 복구 스크립트는 허용목록에 둔 고정 Python 함수다. LLM 출력이나 요청 본문을 실행 인자로 쓰지 않는다
- 같은 사건은 lease로 한 Worker만 실행하고, Worker가 재시작돼도 끝난 조치를 반복하지 않는다. 결과를 확인할 수 없는 조치는 성공으로 추정하지 않는다
- 사건은 Verification이 필수 검사(연속 정상 · 기능 샘플 · 데이터 무결성)를 모두 통과시켰을 때만 `recovered`가 된다. 한 검사라도 실패하면 남은 안전한 전략으로 돌아가거나 `failed` · 승인 대기로 끝낸다

### 8.2 사건 처리 상태

```mermaid
stateDiagram-v2
    [*] --> detected: 감지 기준 충족
    detected --> recovering: 진단 완료 · lease 획득
    detected --> awaiting_approval: UNKNOWN · 승인 필요
    recovering --> recovering: 액션 fail/timeout, 상한 내 다음 단계
    recovering --> verifying: 액션 단계 완료
    verifying --> recovered: 필수 검사 전체 통과
    verifying --> recovering: 허용된 추가 전략이 남음
    recovering --> failed: 상한 · 전체 제한 초과
    verifying --> failed: 기능 · 무결성 검사 실패
    awaiting_approval --> recovering: 승인
    awaiting_approval --> manual_check: 거부
    failed --> awaiting_approval: 사람 판단 필요
    recovered --> [*]
```

- 상태 변경은 healing DB 트랜잭션으로 기록한다. 승인 API는 운영자 결정을 기록하고 상태만 바꾸며, 액션은 Recovery Worker가 실행한다
- `failed` · `awaiting_approval` 동안에는 자동 조치를 재개하지 않는다
- 운영 대시보드에서 `incident_id`로 사건 타임라인 · `recovery_plan` · 복구 시도 · 검증 결과를 조회한다
- 앱 복제본 장애(F-3)는 Gateway가 Recovery보다 먼저 장애 복제본을 트래픽에서 빼고 새 요청을 정상 복제본으로 보낸다. 그 뒤 Recovery Worker가 다른 복제본이 healthy인지 확인하고 재시작 · 재개한다. 전환은 요청 경로 복구일 뿐 실패한 요청의 재처리가 아니다

| SC-3  | MTTR                           | F-1 · F-2 · F-5 · F-6 **60초**, F-3 프로세스 중단 **90초** 이하                                       | 그 시간 안에 정상화(`recovered`)      |

### 9.1 무인 복구율 산정

`무인 복구율 = 수동 개입 없이 정상화된 유효 회차 수 ÷ 유효 장애 주입 회차 수 × 100`

- **분모**: F-1 · F-2 · F-3 · F-5 · F-6 각 5회 = 25회. 주입 도구 오류 · 준비 실패 회차만 증거를 남겨 무효로 하고 다시 수행한다. 사람이 개입해야 끝난 회차는 분모에 남기고 실패로 센다
- **성공**: 사람의 승인 · 재시작 · 설정 변경 · 데이터 수정 없이 검증을 모두 통과해 `recovered`가 된 회차. 안전한 승인 대기 · 수동 점검 · `failed` 전환은 SC-6으로 따로 세고 성공에 넣지 않는다
- **시간**: MTTD는 주입 시각 → 사건 감지 시각, MTTR은 주입 시각 → `recovered` 기록 시각
- 결과 보고 표 양식은 자동장애복구 계획서 7절을 쓴다. 측정 전 값은 `미측정`으로 둔다

### 9.2 시험 · 배포 게이트

- **배포 차단**: 자동 복구 단위 · 통합 시험 실패, SC-5 무결성 위반, SC-6 에스컬레이션 누락이면 배포하지 않는다
- **정적 검사(lint) 실패**도 테스트 실패와 같이 배포를 차단한다(CI 필수 검사)
- **이중화 배포 시험**(DEP-1 ~ 5: 매니페스트 · 시크릿, 탐색 · 분산, A/B 장애 전환, 부분 장애 · 복귀, 사용자 상태)과 자동 복구 시험 절차는 자동장애복구 계획서 8절을 따른다
- **순차 배포**: 앱 스택은 A를 먼저 교체하고, 게이트웨이에서 A가 UP으로 재등록된 것을 확인한 뒤 B를 교체한다. 두 스택을 동시에 내리지 않는다
- 시험 전제(공용 스택 + 앱 스택 A/B가 모두 떠 있고 healthy)를 못 맞추면 복구 실패가 아니라 배포 구성 실패로 따로 보고한다

### 9.3 비기능 요구사항

| 구분          | 내용                                                                                                                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 신뢰성        | 재시작해도 시도 횟수 · 사건 상태 · lease · 체크포인트가 남는다. 앱 복제본 하나가 죽어도 서비스는 계속된다                                                                                                                          |
| 안전성        | 장애 주입 · 자동 복구는 실습 환경에서만, 복구 실패 시 잘못된 주문서를 만들지 않는다                                                                                                                                                  |
| 보안          | 관리 링크는 추측 불가 토큰, 공유 카드 · 로그에 토큰 원문 없음. Recovery Worker에 광범위한 Docker 제어 권한을 주지 않는다                                                                                                             |
| 운영 대시보드 | 비밀번호 하나로 진입, 값은 `.env`의 `OPS_DASHBOARD_PASSWORD`에만. 같은 값으로 서비스 진입 게이트(G-0)도 연다(3절)                                                                                                                 |

| 배포 구성     | Docker Engine 1대 · `docker-compose.core.yml` 1벌 + `docker-compose.app.yml` 2벌(`moa-a` · `moa-b`) + 운영 대시보드 전용 1벌(`moa-ops`), 외부 포트는 8501(게이트웨이)과 8502(운영 대시보드 · 모두에게 공개, 비밀번호로 보호), 비밀값은 `.env`만, 업무 처리 컨테이너는 `restart: "no"`, 컨테이너마다 메모리 제한 |
| 사용성        | 모바일에서도 사용 가능, 해요체 · 쉬운 말, 내부 용어 노출 0건, 처음 쓰는 5명 중 4명 이상이 도움말 없이 첫 정리 완료                                                                                                                   |

| 변경 요청 받기             | 주문서를 한 번 공유하고 바꿀 것만 답장으로 받는 방식. 붙여넣은 답장 중 분명한 변경은 바로 반영, 불분명한 것은 확인 질문. 사람별 확인 상태 없음       |
| 공유 = 완료                | 텍스트 복사 · 이미지 저장을 하는 순간 완료 처리되고 버전이 고정된다                                                                                 |
| Snapshot                   | 한 번에 붙여넣은 채팅 전체. **같은 담당자(같은 접근 토큰)가** 같은 내용을 다시 넣으면 기존 결과를 돌려준다. 토큰이 없거나 다르면 새로 분석한다 |
| 주문 해석 서비스           | Interpreter. 주문 문장을 정해진 형식(JSON)으로 바꾸는 LLM 서비스. Primary(1차) · Backup(대체) 2계통, 둘 다 실패하면 규칙 해석(5.5)                  |
| 체크포인트                 | 마지막으로 성공한 처리 단계 기록. 중단돼도 여기서부터 이어간다                                                                                       |
| 사건(incident)             | Monitor가 만드는 장애 단위. 주입 · 탐지 · 복구 · 정상화 시각을 가진다                                                                             |
| 장애 코드                  | Diagnosis 분류 7종: WORKER_DOWN · DEP_HTTP_5XX · DEP_TIMEOUT · REPEATED_FAILURE · AGENT_OUTPUT_INVALID · DB_UNAVAILABLE · UNKNOWN              |
| MTTD · MTTR               | 장애 후 탐지까지 · 정상화까지 걸린 시간                                                                                                             |
| 무인 복구율                | 수동 개입 없이 정상화된 유효 회차 ÷ 유효 장애 주입 회차 × 100                                                                                      |
| 앱 복제본(앱 스택)         | 같은 `docker-compose.app.yml`을 프로젝트 이름만 바꿔 띄운 frontend + backend 묶음 A(`moa-a`) · B(`moa-b`)                                     |
| 공용 스택 · 게이트웨이    | 앱 스택이 함께 쓰는 게이트웨이 · DB · 주문 해석 서비스 · healing 묶음(`moa-core`). 게이트웨이는 정상 앱 스택에만 요청을 보내는 HAProxy          |
| lease                      | 한 사건을 한 Recovery Worker만 소유하게 하는 DB 임대. 만료되면 다른 Worker가 이어받는다                                                              |
| 회로 차단                  | 같은 장애가 3번 연속 나면 자동 복구를 멈추는 장치                                                                                                    |
| 허용목록                   | 자동 재시작해도 되는 대상 목록                                                                                                                       |
| 에스컬레이션               | 자동으로 못 고친 사건을 상태를 보존한 채 운영자에게 넘기는 일                                                                                        |
| Validation · Verification | 앞은 주문 내용 검증(업무 층), 뒤는 복구 결과 검증(장애 대응 층)                                                                                      |
