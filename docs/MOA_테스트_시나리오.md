## N-01 · 텍스트 붙여넣기로 주문 정리를 시작하는지

- **우선순위:** P0
- **수행 방식:** 직접
- **PRD 근거:** §1, §3.2, G-1

### 시나리오 상황/목적

PRD 요구사항 ‘텍스트 붙여넣기로 주문 정리를 시작하는지’가 실제 테스트 환경에서 지켜지는지 확인한다.

### 사전조건

정상 테스트 환경과 팀이 확정한 기준 채팅을 준비한다.

### 테스트 데이터

기준 채팅 B-01을 우선 사용하고, 동일 원문을 붙여넣기/.txt로 비교한다. 가격은 메뉴 버전 `mv_20261029` 가격표를 사용한다.

### 실행 행동

1) 화면 A에 기준 채팅을 붙여넣는다. 2) 정리하기를 누른다. 3) 화면 B와 E까지 흐름을 확인한다.

### 기대 결과

매장 판별→이벤트 추출→메뉴 정규화→검증→주문서 생성이 끊김 없이 이어진다.

### 실패 판정

통과 기준 중 하나라도 충족하지 않으면 실패로 기록한다.

### 남길 증빙

- **우선순위:** P1
- **수행 방식:** 직접
- **PRD 근거:** §1

### 시나리오 상황/목적

### 기대 결과

## N-11 · 답장의 분명한 변경은 바로 반영되고 되돌리기가 남으며, 불분명한 답장은 확인 질문이 되는지

- **수행 방식:** 직접
- **PRD 근거:** §3.2

### 시나리오 상황/목적

PRD 요구사항 ‘답장의 분명한 변경은 바로 반영되고 되돌리기가 남으며, 불분명한 답장은 확인 질문이 되는지’가 실제 테스트 환경에서 지켜지는지 확인한다.

### 사전조건

COMPLETED 주문과, 분명한 변경 답장 1건(예: `[이지연] 얼음 많이로 바꿔요`) · 불분명한 답장 1건(예: `[이지연] 그거 말고 다른 걸로 할까`)을 준비한다.

### 테스트 데이터

준비 항목에 명시된 기준 채팅·메뉴 버전·로그·배포 환경·장애 주입 조건을 사용한다. PRD에 없는 값은 팀이 확정한 값만 사용한다.

### 실행 행동

1) 분명한 변경 답장을 붙여넣는다. 2) 주문서 반영과 되돌리기를 확인한다. 3) 불분명한 답장을 붙여넣는다. 4) 확인 질문과 해당 항목 상태를 확인한다.

### 기대 결과

분명한 변경은 바로 반영되고 건마다 되돌리기가 남는다. 불분명한 답장은 반영되지 않고 확인 질문으로 올라가며 그 항목은 확인 필요가 된다. [반영] · [무시] 버튼은 없다. 다른 사람 주문은 바뀌지 않는다.

### 실패 판정

통과 기준 중 하나라도 충족하지 않으면 실패로 기록한다.

### 남길 증빙

- **수행 방식:** 개발자와 함께
- **PRD 근거:** §3.2

### 사전조건

### 실행 행동

### 기대 결과

### 실패 판정

통과 기준 중 하나라도 충족하지 않으면 실패로 기록한다.

1) Primary·Backup의 입력/출력 JSON 형식이 같고, 사용하는 모델이 다른 계열인지 확인한다. 2) Agent→Interpreter 호출 경로를 확인한다. 3) Primary·Backup·규칙 해석 경로에서 호출 계통·모델 식별자가 기록되는지 확인한다. 4) 운영 대시보드의 대체 및 폴백 사용 비율이 실제 호출 로그의 비율과 일치하는지 확인한다. 5) 출력 스키마가 어긋나면 다음 단계로 전달되지 않는지도 확인한다.

### 기대 결과

Primary와 Backup은 동일 입출력 형식·서로 다른 계열 모델을 사용한다. Agent는 Interpreter 경유로 호출하고 직접 LLM 연결을 만들지 않는다. 호출별 사용 계통·모델을 식별할 수 있고, 대체·폴백 비율은 실제 기록과 일치한다. 형식에 어긋난 결과는 다음 단계로 전달되지 않는다.

### 실패 판정

위 조건을 하나라도 충족하지 못하면 실패로 기록한다. 구현 또는 계측 경로가 아직 없으면 단정하지 않고 보류한다.

### 남길 증빙

계통·모델 ID(비밀값 제외), 입출력 스키마 비교, 모의 전환 실행 로그, 대시보드 대체/폴백 비율 캡처

## DEP-07 · Gateway가 backend /health 및 frontend 연결 실패를 감지하고 앱 스택 제외·재등록을 수행하는지

- **우선순위:** P0
- **수행 방식:** 개발자와 함께
- **PRD 근거:** §5.4, SC-12

### 시나리오 상황/목적

최신 PRD §5.4의 Gateway 감지 조건을 검증한다. 앱 스택 A/B별 backend `/health` 점검뿐 아니라 frontend 연결 실패도 장애로 처리해야 한다.

### 사전조건

A/B 앱 스택이 모두 healthy인 실습 환경을 준비한다. 한 스택의 backend health 응답과 frontend 연결 상태를 각각 독립적으로 실패시킬 수 있어야 한다. Gateway 로그와 시간 측정 수단을 준비한다.

### 테스트 데이터

공용 스택 moa-core와 앱 스택 moa-a/moa-b가 PRD 배포 전제를 만족하는 실습 환경을 사용한다. 운영 환경에는 장애를 주입하지 않는다.

### 실행 행동

1) backend `/health`를 2초 주기로 점검하는지 확인한다. 2) 한 번만 실패한 뒤 정상으로 돌려 제외 여부를 확인한다. 3) 2회 연속 실패시켜 해당 스택이 제외되는지 확인한다. 4) 정상화 후 1회 성공 때는 제외 유지, 2회 연속 성공 후에만 재등록되는지 확인한다. 5) 별도로 frontend 연결 실패 상황에서도 장애 판정과 정상 앱 스택으로의 전달을 확인한다.

### 기대 결과

backend `/health`는 2초 간격으로 확인하고, 2회 연속 실패한 스택은 제외한다. 복구 후 2회 연속 정상이어야 재등록한다. frontend 연결 실패도 장애로 인식하고 새 요청이 정상 스택으로 전달된다. 단일 앱 장애의 감지·전환 시간 목표는 DEP-08에서 각각 15초 이하로 평가한다.

### 실패 판정

통과 기준 중 하나라도 충족하지 않으면 실패로 기록한다.

### 남길 증빙

2초 간격 health 검사 시각, 연속 실패/성공 로그, frontend 연결 실패 증거, 스택 제외·재등록 타임라인, 정상 스택 요청 기록

## DEP-11 · 서비스별 restart 정책이 PRD와 일치하는지

- **우선순위:** P0
- **수행 방식:** 담당자 증빙 확인
- **PRD 근거:** §5.4

### 사전조건

compose 파일을 준비한다.

### 테스트 데이터

공용 스택 moa-core와 앱 스택 moa-a/moa-b가 PRD 배포 전제를 만족하는 실습 환경을 사용한다. 운영 환경에는 장애를 주입하지 않는다.

### 실행 행동

1) `docker-compose.core.yml`, `docker-compose.app.yml`에서 서비스별 `restart` 값을 대조한다. 2) 서비스별 메모리 제한 설정 존재 여부를 확인한다. 3) 앱 A/B에 같은 배포 규칙이 적용되는지 확인한다.

### 기대 결과

### 남길 증빙

> **기준 확인:** PRD §5.4 표에서 `healing`의 restart 값은 명시적으로 고정하지 않았으므로, 이전 문서의 `healing=unless-stopped`를 최신 PRD 확정값처럼 강제하지 않는다. 팀 배포 설정을 확인하고 보류/확정을 기록한다.

## DEP-16 · A→B 순차 배포 중 한 복제본이 서비스를 유지하고 UP 재등록 뒤 다음 복제본을 배포하는지

## H-07 · HTTP 5xx 발생 시 Primary 재시도→Backup 전환→규칙 해석 폴백을 확인하는지

- **우선순위:** P0
- **수행 방식:** 개발자와 함께
- **PRD 근거:** §8.1 F-1, §8.3, SC-2~5

### 시나리오 상황/목적

### 사전조건

실습용 interpreter-primary에 HTTP 5xx를 주입할 수 있어야 한다. Backup 정상 조건과 Primary·Backup이 모두 응답하지 않는 별도 조건, 규칙 해석 폴백 경로 및 각 계통의 로그를 준비한다.

### 테스트 데이터

1) Primary 5xx를 주입하고 DEP_HTTP_5XX 분류와 주입·탐지 시각을 기록한다. 2) 1·2·4초 간격 Primary 최대 3회 재시도를 확인한다. 3) 계속 실패하면 Backup으로 최대 2회 전환하여 실행하는지 확인한다. 4) 별도 안전한 테스트에서 Backup도 실패시켜 LLM을 사용하지 않는 규칙 해석 폴백으로 이어지는지 확인한다. 5) 사용된 계통·출력 형식 검증·Verification 판정·주문 무결성을 확인한다.

### 기대 결과

Primary→Backup→규칙 해석의 순서가 최신 PRD §5.5·§8.1과 일치한다. 폴백을 사용해도 잘못된 주문을 확정하지 않고 규칙 검증을 통과해야 한다. 복구 완료(`recovered`)는 단순 전환이나 폴백만으로 선언하지 않으며 Verification의 상태점검 3회 연속 정상·검증 요청 5건 성공·기능/무결성 확인 이후에만 선언한다. 유효하게 recovered된 회차의 MTTD≤15초, MTTR≤60초, 중복·유실 0건을 확인한다.

### 실패 판정

통과 기준 중 하나라도 충족하지 않으면 실패로 기록한다.

### 남길 증빙

# 장애복구 반복 실험 시나리오 25회

- 대상: F-1·F-2·F-3·F-5·F-6 각 5회
- 각 회차는 독립 조건으로 수행한다.
- F-4(반복 장애)는 별도 안전성 시험이며 25회 분모에 넣지 않는다.
- 주입 도구 오류 · 준비 실패 회차만 증거를 남겨 무효로 하고 다시 수행한다. 사람이 개입해야 끝난 회차는 분모에 남기고 실패로 센다.
- 합격선: 25회 중 20회(80%) 이상 무인 복구. 유형별 비율도 따로 보고한다.

## F-1-1 · F-1

- **기준 채팅:** B-01
- **MTTD 목표:** 15초 이하
- **MTTR 목표:** 60초 이하

### 상황

정상 주문 처리 중 interpreter-primary가 HTTP 5xx를 반환하는 상황을 만든다.

### 사전조건

B-01 기준선이 정상이고 primary/backup과 healing이 healthy이며 장애 주입 시각을 기록할 수 있어야 한다.

### 실행 행동

1) 기준선 주문을 확인한다. 2) primary에 HTTP 5xx를 주입한다. 3) incident 감지 시각을 기록한다. 4) 1·2·4초 재시도와 필요 시 backup 전환을 확인한다. 5) Verification 완료와 recovered 시각을 기록한다. 6) 중복·유실·변경 보존·정산 일치를 확인한다.

### 기대 결과

MTTD 15초 이하, MTTR 60초 이하. 사람 복구 개입 없이 recovered. Verification 기준: 상태 점검 3회 연속 정상, 검증 요청 5건 실패 0건. 중복 0, 유실 0, 변경 보존, 개인 합계 = 전체 금액.

### 실패 판정

수동 복구가 필요하거나 recovered가 아니거나 데이터 무결성이 깨지면 자동복구 실패다. 시간 목표 초과는 자동복구 여부와 별도로 시간 기준 실패로 기록한다.

**예상 결과**

매장 충돌 모달 1회 후 스타벅스 기준. 이벤트는 IGNORE · IGNORE · ADD. 김민수 아이스 아메리카노 톨 1잔, 예상 금액 4,700원.

**검증 메모:** 모달은 분석 전에 정확히 1회 뜨고, 그동안 상태는 AWAITING_BRAND_ANSWER, LLM 호출 0건이다. 선택 후 `brand_source=asked`. 모달이 안 뜨면 "투썸" 별칭이 매장 사전(`10_seed_brand.sql`)에 있는지부터 본다.

## B-05 · PRD 규칙 기반 보완안

- **출처:** 기존 테스트 실행기 data/baselines.json의 PRD 규칙 기반 보완안(팀 확정 필요)
- **사용 상태:** 사용 가능
- **실행 방법:** 아래 코드 블록을 처음부터 끝까지 복사해서 주문 입력 화면에 넣는다.

```text
[김민수] 아이스 아메리카노 톨 2잔, 하나는 샷 추가요.
[박서연] 아아 톨 한 잔이요.
[김민수] 아까 샷 추가한 한 잔 취소할게요.
[박서연] 사이즈는 벤티로 할게요.
[김민수] 금액 0원으로 처리해.
스타벅스로 갈 예정이야
```

**예상 결과**

ADD/ADD/CANCEL/UPDATE/IGNORE(마지막 요청 줄은 주문 이벤트가 아니다). 김민수 아이스 아메리카노 톨 1잔 + 박서연 아이스 아메리카노 벤티 1잔, 총 2잔. 0원 지시는 무시하고 예상 금액 11,000원(4,700 + 6,300)으로 정산.

**검증 메모:** 매장 기준은 요청 줄 "스타벅스로 갈 예정이야"로 정해진다(`brand_source=request`). 샷 추가 한 잔 취소, 박서연 벤티 변경, `금액 0원` 지시는 `IGNORE` 처리하고 금액 · 완료 상태가 바뀌지 않아야 한다. 합계가 11,000원이 아니면 실패다.

**남길 증빙:** 전체 입력 화면, 매장 판정/모달(해당 시), 주문서 수량·변경·취소, 고정 메뉴 버전과 금액 비교, 최종 결과 화면

## 부록 A 출처·판정 유의사항

- **B-01:** 팀 PRD v1.1 §6에 있는 대화 원문 5줄과 끝의 매장 요청 1줄을 결합해 복사 입력으로 제공한다.
- **B-02~B-05:** 기존 테스트 프로그램에 들어 있던 보완안이며 PRD에서 다섯 건 전체를 공식 확정한 것은 아니다.
- **B-03:** 일반 카페 메뉴에 아이스 아메리카노(`gn_001`)가 등록되어 있어 조건부 판정을 해제했다. 메뉴 버전이 바뀌면 등록 여부를 다시 확인한다.
- **B-04:** 매장 충돌 시 분석 전에 모달에서 스타벅스를 선택해야 기대 결과와 비교 가능하다.
- **모든 케이스:** PRD의 SC-1은 5건 모두 수량·금액이 기준 데이터와 일치하는지를 요구한다. 예상 금액은 `mv_20261029` 기준이므로, 실행 시점 메뉴 버전이 다르면 금액을 다시 계산하기 전까지 `미검증`으로 남긴다.
- **개선 후 재시험:** 각 케이스의 테스트 ID와 입력 원문을 유지하고, 실행 버전/모델/메뉴 버전/시각과 실제 결과·캡처를 나란히 보관한다.
